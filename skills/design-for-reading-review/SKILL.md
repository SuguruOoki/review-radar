# 読む負担を減らす設計レビュー

「呼び出し側は、公開された契約から何を判断できるか」を確認する。内部を追わなければ分からない条件や状態変更を見つけ、既存の正確性・可読性・設計レビューへ統合する。別のレビュー工程や採点表を増やさない。

## いつ使うか

- PR前のセルフレビューで「設計の観点」を足すとき
- 生成コード・急ぎの実装をレビューするとき（信頼できないコードほど読む量が増える）
- Review Radar のレポートで `design` シグナルが付いた候補を読むとき
- 「リーディングコスト」「読む量」「契約」「副作用」「抽象化」の観点を求められたとき

使わないとき: 型の証拠だけの機械チェック（`anti-slop`）、UIデザインの視覚レビュー（`design-review`）、多軸の総合レビュー本体（`code-review-and-quality` がこの観点を呼び込む）。認可・決済・性能・並行性のレビューは置き換えない。

## 進め方

1. レビュー対象の差分と要件を確認し、変更単位で **ASIS・TOBE・理由・意図** を短く整理する。すでに整理済みなら再利用する。
2. Review Radar が使えるなら先に走らせ、`design` シグナルが付いた hunk を起点にする（後述の「Review Radar 連携」）。シグナルは「疑わしい箇所の優先度上げ」であり欠陥検出ではない。
3. hunk が属する関数・メソッドを特定し、その本体と呼び出し元を読む。hunk 単位の字句一致だけで断定しない。
4. 変更した公開関数・型の契約を、要件と利用側の期待から把握する。既存テストや現在の実装だけを仕様の根拠にしない。不明な業務条件は推測で決めず、未確認として扱う。
5. 下の観点で、今回の差分が導入・悪化させた問題を具体化する。既存の問題は区別し、変更に必要な範囲で提案する。

レビューだけの依頼では修正を始めない。実装後のセルフレビューでは、任された範囲の修正・検証へ戻る。

## 設計のチェック観点

### 1. 契約による設計

メソッド実行前の**事前条件**、実行後の**事後条件**、インスタンス生存中の**不変条件**の3つが、型・名前・入口のガード節・テストのどれかで利用側から読めること。読めなければ、挙動を確かめるために内部を読まされる。

確認すること:

1. 追加・変更した公開メソッドの事前条件（受け入れる入力の範囲）は、呼び出し側から読み取れるか。スライドのBMI例（`bmi(heightMeter, weightKg)` の「0<身長≤3」「0<体重≤700」）のように、実装本体を読まずに受け入れ範囲が言えるか
2. 事後条件（戻り値が何を表すか・失敗時にどこまで状態が変わるか）は、実装を読まずに判断できるか
3. 型に不変条件（Quantity の MIN=1/MAX=20 のような範囲・整合性）があるなら、生成時に検証されているか
4. その不変条件は、生成後の更新経路（setter・ミューテーションメソッド・公開コレクション）や参照共有でも破られないか
5. 事前条件に違反したときの振る舞い（例外の型・エラー表現）が契約として書かれ、呼び出し側が前提に扱えているか
6. 契約がテストコードの基準になっているか（設計で決めた条件→テスト→プロダクトコードの順に対応し、呼び出し回数や内部構造の固定だけで終わっていないか）
7. 型・既存の境界で保証済みの条件に、重複した実行時検証を要求していないか（[good] として残す）

指摘の例:

```text
[must] src/domain/bmi.ts:12 — bmi() の事前条件が見えないですね。heightMeter に 0 や負値が来ても、
0 なら ±Infinity、負値なら h² で正の身長と同じ"それらしい"値が返って、呼び出し側は普通の結果と同じ顔で
受け取っちゃいそうです。入口にガード節（例: `if (heightMeter <= 0 || 3 < heightMeter) throw ...`）を置くと、
シグニチャだけで受け入れ範囲が読めるようになりそう〜
```

```text
[must] src/domain/quantity.ts:34 — コンストラクタで MIN/MAX を検証してるのは良いんですが、setValue() が
そこを通らずに 20 超えを作れてしまうかもです。不変条件が「生成時だけ」の約束に読めてしまいますね。
setValue() でも同じ検証を通すか、値を変えずに新しい Quantity を返す形にすると、入口だけで契約が読めそう〜
```

### 2. 副作用のない関数

副作用 =「引数を受け取り戻り値を返す以外に外部の状態を変更すること」（インスタンス変数・グローバル変数の変更、参照型引数の変更、DB/ファイルI/O）。副作用があると事前条件・事後条件が暗黙的になり、**シグニチャを見ただけでは何が起こるか分からず、内部の具体コードを読みに行かなければならない**。

確認すること:

1. 変更した関数は、引数→戻り値以外に外部状態を変えていないか。シグニチャだけで挙動が予測できるか
2. インスタンス変数・グローバルへの代入が、コンストラクタの初期化や意図的な状態更新か、計算中に混入した副作用かを区別できるか
3. 参照型引数を書き換えていないか（呼び出し側のオブジェクトの状態が、戻り値として見えないまま変わる）
4. 時刻・乱数・環境変数など、同じ引数で結果が変わる隠れた依存を読み手が見つけられるか
5. DB・ファイル・通知などのI/Oは、目的と失敗時の扱いが明確な境界に隔離されているか（なくせない副作用は隔離し、可能な限り純粋関数を）
6. 値を表す型（等価・検証・派生の意味を持つ型）が書き換え可能になっていないか。immutable にできるか

指摘の例:

```text
[must] src/order/estimate.ts:20 — 見積り計算のはずが、引数の注文オブジェクトのフィールドを直接更新してますね。
呼び出し側からすると「計算しただけ」のつもりで渡したオブジェクトが変わってて、戻り値だけ見てると気づけない
かもです。計算結果を新しいオブジェクトで返す形にするか、更新するなら関数名と doc で契約に書くのがよさそう〜
```

### 3. 抽象化

制御抽象化（条件分岐・ループ・サブルーチン。関数はその一種）とデータ抽象化（データ構造と操作方法をひとまとめに型として定義）。適切に抽象化すると**「中身を気にせず使える」**。それは「仕様通りに動作するはずだと**信頼している**」ということで、内部の具体コードを読みに行かずに済む。

確認すること:

1. 呼び出し側が業務上の目的を読めるか（`CallCharge` のように計算規則が境界の内側へまとまっているか）
2. 利用側が内部の手順・表現に依存していないか。4段以上のプロパティ連鎖（`user.profile.wallet.balance` のような）で内部構造に依存していないか
3. 状態・種別を文字列リテラルとの比較（`status === "active"` のような）で判別していないか。列挙・専用型・定数にできるか
4. 抽象化の価値は「隠せる規則・守れる条件・利用側の依存が減るか」で判断する。行数の減少や利用回数だけを合否基準にしない。一度だけ使う関数にも、意味のある境界を設ける価値はあり得る
5. 名前の修正・関数抽出・既存の型の利用で足りるかを先に考える。クラス・共通レイヤー・汎用フレームワークの追加を定型の改善案にしない

指摘の例:

```text
[nits] src/billing/report.ts:8 — `user.profile.wallet.balance` まで掘ってると、wallet の内部表現が変わったら
ここも壊れるし、読み手は wallet の構造を知らないと読めないですね。`user.walletBalance()` みたいな形で
wallet 側に聞くようにすると、中身を気にせず使えるようになりそう〜
```

## 指摘の書き方

重要度の付け方:

- **[must]**: 具体的な失敗経路（どの入力・どの呼び出しで何が壊れるか）を示せる場合のみ。契約の変更が呼び出し側に波及する場合も含む
- **[nits]**: 提案レベル。設計上の懸念だけで重大なバグと断定しない
- **[good]**: 保証済みの条件・きれいな契約を残す。違反への要求ではない

各指摘を次の内容で短く書く（既存のレビュー形式・重要度表記に合わせる）:

```text
[重要度] file:line — 設計上の問題
根拠: 現在のコードと確認した契約・利用側の期待
影響: どの条件で誤動作するか、または何を追わないと安全に変更できないか
改善: その問題を解消する最小限の変更
検証: 期待する入出力・状態の変化、または変化しないこと
```

- 不正な状態・誤った結果に到達する経路が確認できたら具体例を示す。「責務が多い」「抽象化が足りない」だけで終えない
- 仕様が未確認なら確認事項として分ける。未変更の負債や好みの違いを今回の必須修正にしない
- カジュアルに、同僚と話す口調で書く（〜ですね、〜かも、〜よさそう）

## Review Radar 連携

Review Radar v0.2.1 の heuristic プロバイダは、以下の `design` シグナルを検出する（いずれも非必須・テストファイル対象外）:

| シグナル | 検出する字句 | 主な偽陽性 |
| --- | --- | --- |
| design-contract-removed | 削除行の throw / assert / require 系 | 検証の移設・例外型の変更（意図的な契約変更） |
| design-side-effect-write | 追加行の this / self / globalThis 等への代入 | コンストラクタの初期化 |
| design-unchecked-arithmetic | 追加行に算術・parse があり同じ hunk にガードなし | ガードが hunk 外（呼び出し元・上位バリデータ）にある |
| design-stringly-typed | 文字列リテラルとの比較による判別 | typeof・環境変数の慣用的な比較 |
| design-leaky-abstraction | 4段以上のプロパティ連鎖 | 慣用的な名前空間アクセス |

挙動: design シグナルが付いた候補は「人間の判断」軸が 0.625 以上になり `human_review` ルートに載る。ガード削除は「失敗時の影響」も引き上げる。「境界の変更」軸は design では上げない。レポートの質問欄に design の確認質問が表示される。

```bash
node dist/cli.js scan --repo /path/to/repo --base origin/main --head HEAD --merge-base \
  --provider heuristic --out ./review-output
```

拾えないもの（本スキルの手動パスで補う）: 契約の「不在」そのもの、条件式と業務ルールのずれ（`<` と `<=`・単位混在）、setter・参照共有をまたぐ不変条件、参照型引数の書き換え、テストが契約を検証しているか。字句一致はコメントやテストにも当たり得る。**シグナルは疑わしい箇所の優先度上げであり、欠陥の検出ではない。**

## 完了条件

- 3つの観点＋契約の検証を、変更した公開関数・型に対して実施した
- Review Radar を実行し、design シグナルが付いた候補を読んだ（使えない環境ではその旨を残す）
- 指摘は直すか、直さない理由を残した。[must] は具体的な失敗経路付きで書いた
- 確認した境界と検証の有無、残る未確認事項を簡潔に報告した。実行していないテストを成功扱いにしない
- 指摘ゼロも許容する

上記は資料の主題。指摘形式、重要度の判断、時刻等の隠れた依存の確認、魔法数・文字列判別の抑制、過剰設計の抑制（全関数に実行時検証を足さない）は、レビューへ適用するための運用基準であり、発表者の逐語的な主張ではない。契約を書いたことやテスト成功だけで、正しさ全体が保証されたとは扱わない。
